# Shipping ProfSchedule AI on Google Play

The app is a PWA, so the route to Play is a **Trusted Web Activity** — a thin
Android shell that opens the live site full-screen, with no browser UI. Google
builds and endorses this path; it is not a repackaging trick.

What that means in practice: **the Android build is a shell, and the app is
still the website.** Ship a fix to Render and every installed copy has it
immediately, with no store review. The only reasons to rebuild the Android
artifact are a new icon, a new name, or a permissions change.

---

## What could not be done for you, and why

The build needs a JDK and the Android SDK, neither of which is installed on
this machine, and it needs a **signing key that only you should ever hold**.
A keystore is the identity of your app on Play: anyone with it and its
password can publish an update to your listing. It must not be generated by
someone else, committed to git, or pasted into a chat.

So this directory contains everything except the two things that are
rightfully yours: the key, and the machine that runs the build.

**Also worth knowing:** Play has not accepted APKs for new apps since August
2021. The upload format is an **AAB** (Android App Bundle) — `bundle` below
produces it. An APK is still useful for testing on your own phone.

## One-time setup

1. **JDK 17** — https://adoptium.net
2. **Android SDK command-line tools** — either Android Studio, or the
   standalone tools, then set `ANDROID_HOME`.
3. **Bubblewrap**

   ```bash
   npm install -g @bubblewrap/cli
   ```

4. **A Play Console account** — one-off US$25.

---

## Build

From this directory, with `REPLACE-WITH-YOUR-DOMAIN` in `twa-manifest.json`
swapped for your real host (no `https://`, no trailing slash):

```bash
npx @bubblewrap/cli init --manifest https://YOUR-DOMAIN/manifest.json
```

Bubblewrap will offer to create the keystore. Let it, choose a strong
password, and then **back that file up somewhere you will still have it in
three years** — losing it means you can never update the listing again, only
publish a different app.

```bash
npx @bubblewrap/cli build
```

That writes `app-release-bundle.aab` (upload this to Play) and
`app-release-signed.apk` (sideload this to test on your own phone).

## The step everyone forgets

A TWA only hides the browser's URL bar once the site proves it owns the app.
Without it the app works but shows your domain in a bar across the top, which
is exactly how it reads as a website in a jacket.

1. Get the SHA-256 fingerprint of your **upload key**:

   ```bash
   keytool -list -v -keystore android.keystore -alias profschedule
   ```

2. After your first upload, get Play's fingerprint too, from
   **Play Console → App integrity → App signing**. Play re-signs what you
   upload, so the certificate users actually get is theirs, not yours —
   **both fingerprints must be listed** or verification fails for everyone who
   installed from the store.

3. Set these on Render and redeploy:

   ```
   ANDROID_PACKAGE_NAME=in.ac.dypcoeakurdi.profschedule
   ANDROID_SHA256_FINGERPRINTS=<upload-key-sha256>,<play-signing-sha256>
   ```

4. Check it:

   ```bash
   curl https://YOUR-DOMAIN/.well-known/assetlinks.json
   ```

   It answers 404 until both variables are set — deliberately, because an
   empty ownership statement is a claim that *nobody* owns the domain, and
   Chrome caches that answer.

## Before you submit

Play will reject a listing that is only a wrapper around a website, so the
app has to genuinely work as an app:

- [ ] `assetlinks.json` returns both fingerprints, and the installed app shows
      **no URL bar**
- [ ] It opens offline to something other than a browser error
- [ ] Notifications arrive (VAPID keys set, and a device registered)
- [ ] A **privacy policy URL** — Play requires one, and this app handles
      timetables, names and departments, so it needs to say so honestly
- [ ] Data safety form completed: it collects name, email, college,
      department, schedule content
- [ ] Screenshots at phone size — the mobile layout is already clean at 320px
- [ ] Target SDK meets Play's current floor (Bubblewrap tracks this; a stale
      CLI is the usual cause of a rejection here)

## Alternatives, honestly

**Capacitor** if you later need real native APIs — a proper camera, contacts,
background location. Heavier, and you would be maintaining an app rather than
a shell.

**Neither.** The PWA already installs to the home screen from Chrome and
Safari, with an icon, offline support and push. If the only goal is "on their
phone", that is free, needs no review, and updates instantly. Play is worth it
for discoverability and for looking official to a college — not for the
capability.
